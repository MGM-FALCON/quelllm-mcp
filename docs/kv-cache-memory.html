KV cache memory: how context changes your VRAM budget

A model's weight file is only part of the memory needed to run it. KV cache memory holds attention keys and values from earlier tokens so the model can reuse them while generating text. A longer conversation can therefore change the memory budget even when the model file stays exactly the same.

This guide explains one transparent calculation and its limits. It accompanies the quelllm-mcp project documentation. It contains no hardware benchmark, measured peak allocation, or claim that a particular model will fit your GPU.

Separate model weights from a running session

Weights are the model's learned parameters. The cache is working data for a particular session. They can use different data types: a four-bit weight file does not tell you the cache's precision. Check the runtime's actual cache settings rather than inferring them from a filename.

For standard decoder attention, the keys and values kept at each layer have dimensions for batch, key/value heads, cached tokens, and head size. The Transformers cache explanation describes this storage. Other allocations still matter, including temporary computation buffers and runtime overhead. Adding a cache estimate to weight size does not produce a verified total.

Calculate KV cache memory from explicit assumptions

For identical full-attention layers with equal key and value head dimensions, a simple tensor-size calculation is:

M_KV = 2 × B × L × H_KV × D × T × S bytes

Here, B is the number of independent sequences; L is the layer count; H_KV is the number of key/value heads; D is the dimension of each head; T is the tokens stored per sequence; and S is bytes per cached scalar. The factor two accounts for keys and values. This is arithmetic derived from the tensor dimensions, not a measured allocation.

Use key/value heads, not automatically the number of query heads. Architectures using grouped-query attention can have fewer key/value heads than query heads. Reading the wrong field from a model configuration can distort the estimate before any runtime overhead enters the picture.

Consider a hypothetical configuration: L = 32, H_KV = 8, D = 128, S = 2, and B = 1. It stores 131072 bytes per token, or 128 KiB. The table uses binary units: NIST defines a GiB as 2^30 bytes.

Why context length and parallel requests matter

Within this example, keeping more tokens increases cache storage linearly. Two equally long, independent sequences double the tensor size. This explains why an idle single-user demo and a server handling simultaneous conversations can have different memory needs.

T means stored tokens, which can include prompt and generated tokens. A model's advertised context limit is not proof that every request stores that many tokens. Conversely, a runtime may reserve capacity ahead of use. Ask which quantity your estimate represents: current storage or reserved capacity?

Prefix sharing, request scheduling, cache packing, and memory offload can change what a real server allocates on the GPU. The simple batch multiplier does not model those mechanisms. Read the runtime documentation before treating concurrent requests as identical independent copies.

Check the cache strategy before trusting the table

The Transformers cache strategy guide distinguishes dynamic, static, and quantized caches. A dynamic cache grows as tokens are processed. A static cache preallocates capacity. Layers using sliding-window or chunked attention can stop growing at their respective limits.

KV cache memory therefore does not follow one universal context multiplier across all architectures. Hybrid layers, compressed representations, and unequal layer dimensions need a model-specific calculation. Cache quantization also introduces its own choices and overhead; changing its precision is not the same operation as choosing quantized weights.

Keep a short validation record

Free GPU memory is a snapshot, not the peak demand of a future request. For example, PyTorch's memory-information function reports global free and total device memory. It does not run your workload or predict its peak.

Record the model revision, runtime version, weight format, cache type and precision, requested context, and expected concurrency. Then test a representative prompt and generation length on the actual setup. Keep observed peak memory and failures separate from estimates. This guide has performed no such inference test.
